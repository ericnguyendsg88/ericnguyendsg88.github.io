Requirements case study

AI monitoring MVP for a payments-infrastructure client

Anonymised. The client, systems, regulator, currency, cut-off times, volumes and dates are removed or generalised, and requirement wording is rewritten. Structure, priorities, review outcomes and counts are real.

Summary

The client wanted AI to watch high-value interbank settlement: project each participant's liquidity during the day, and catch unusual transaction behaviour. There was no fixed scope, no production data, and the infrastructure was still being designed. I turned that into an MVP the client, developers and data scientists could all test against.

My role

  • Planned and ran requirements workshops with the client's product strategy and engineering teams.
  • Owned the requirements register and kept it linked to the functional spec by requirement ID.
  • Wrote the data guideline that defined the critical transaction data elements.
  • Broke requirements into user stories and a Jira import, then drafted the UAT test cases.

Process

  1. Kick-off
    Agreed two use cases and their order: liquidity first, anomalies second.
  2. Workshops 1–3
    Settlement logic, the position formula, alert-first monitoring and infrastructure questions.
  3. v0.1
    First register: IDs, type, use case, source and proposed priority.
  4. v0.3
    Client review, round 1. Wording made generic, priorities moved.
  5. Checkpoint
    Data reality check. Added model expectations and staged data delivery.
  6. v1.0
    Client review, round 2. Stories, Jira import and UAT cases traced to IDs.

Key decisions

  • Batch, not real-time. Configurable batch cycles, timed before settlement cut-offs. Real-time went to the parking list (PL-1).
  • Ranges, not exact numbers. A confidence-bounded worst case (LIQ-03) instead of an exact balance forecast (PL-2).
  • Advisory only. Nothing the system produces triggers a settlement or funding action (GEN-03).
  • Five anomaly types. Detection narrowed to five agreed high-priority patterns, each with a UAT scenario (ANM-02).
  • Explain every flag. The client raised explainability from Should to Must (GEN-07).
  • Feedback over auto-tuning. A fixed-category feedback panel (ANM-06) instead of automated retraining (PL-5).

Sample user stories

LIQ-03-US01

As a settlement operator, I want to see each participant's worst-case projected position at the agreed confidence level, so that I can spot a shortfall before the cut-off.

Every monitored participant shows a worst-case value each batch, at the approved confidence level.
GEN-07-US02

As an operator reviewing a flag, I want to see the inputs, threshold and calculation behind it, so that I can judge whether to escalate.

Every flag opens to a breakdown of inputs, logic, threshold and result.
ANM-04-US01

As a support engineer, I want anomaly alerts routed to my team with participant, time window and deviation, so that I can start investigating without another lookup.

An end-to-end test delivers each alert type with all required fields.
ANM-06-US01

As an operator, I want to tag an alert with one feedback category and an optional note, so that the data team can tune the model later.

Exactly one category per alert, optional note, feedback stored.
